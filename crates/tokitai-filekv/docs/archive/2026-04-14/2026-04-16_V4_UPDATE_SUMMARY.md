# FileKV v4.0 战略调整 - 更新总结

**更新日期**: 2026-04-16

**状态**: 战略调整完成

---

## 📋 核心变更

### 从"通用 KV 存储"到"AI Agent 原生持久化层"

| 维度 | v3.0（旧） | v4.0（新） |
|------|-----------|-----------|
| **定位** | 10M+ keys 生产级 KV 存储 | AI Agent 对话上下文存储 |
| **对标** | RocksDB（全面超越） | 无（差异化优势） |
| **目标** | 100K: 161x→50x, 1M: 200x→30x | 对话追加 < 50µs, 分支创建 < 5ms |
| **场景** | 批量随机读写 | 持续追加 + 时间线查询 + 热点缓存 |
| **规模** | 10M+ keys | 100K-1M keys（单次会话） |

## 🎯 新的成功指标

### 不应该比的（已移除）

- ❌ 100K 批量写入 vs RocksDB
- ❌ 纯随机读延迟
- ❌ 10M 规模性能
- ❌ io_uring 异步 I/O
- ❌ SkipList 索引

### 应该优化的（新增）

| 指标 | v0.8.0 当前（估计） | v0.9.0 目标 | AI Agent 场景意义 |
|------|-------------------|-------------|------------------|
| **单条对话追加延迟** | ~200µs | < 50µs | 用户输入响应速度 |
| **分支创建延迟** | ~50ms | < 5ms | 平行探索交互体验 |
| **时间旅行查询** | ~10ms | < 1ms | 回溯历史对话 |
| **加载最近 N 条对话** | ~5ms | < 1ms | 上下文恢复速度 |
| **工具缓存查询** | ~100µs | < 20µs | 工具调用延迟 |
| **内存占用（100K keys）** | ~200MB | < 50MB | 嵌入式部署资源 |
| **启动时间** | ~500ms | < 100ms | AI Agent 冷启动 |

## 💡 关键洞察

### 之前的错误假设

❌ "FileKV 要成为通用 KV 存储，所以必须全面超越 RocksDB"

### 正确的视角

✅ **"FileKV 是 AI Agent 的原生持久化上下文存储"**

**证据**：
1. try-tokitai 项目使用 FileKV 管理对话上下文
2. AI Agent 工作负载特殊（持续追加、时间线查询、热点缓存）
3. RocksDB 不是为 AI Agent 设计的（C++ FFI、配置复杂、无 AI 语义）

### 差异化优势

| 优势 | 描述 | RocksDB 对比 |
|------|------|-------------|
| **Rust 原生** | 零 FFI、类型安全、async 友好 | C++ FFI 开销 |
| **配置简单** | 4 个预设，开箱即用 | 100+ 参数调优 |
| **AI Agent 语义** | 分支、时间旅行、会话 | 无原生支持 |
| **嵌入式部署** | 单二进制，零依赖 | 需要编译、链接 |
