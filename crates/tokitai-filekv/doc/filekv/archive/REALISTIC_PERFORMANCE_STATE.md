# FileKV 真实性能状态报告

> **生成日期**: 2026-04-10  
> **测试环境**: AMD Ryzen 9, Linux  
> **对比基准**: RocksDB (相同硬件、相同数据集)

---

## 📊 真实性能数据

### 1. 热缓存读取 (Hot Cache Read)

| 场景 | FileKV | RocksDB | 差距 | 状态 |
|------|--------|---------|------|------|
| **100 keys (纯 Cache 命中)** | ~107 ns | ~2,500 ns | **23x 快** | ✅ 已验证 |
| **100K keys (真实场景)** | ~151 ms | ~628 µs | **240x 慢** | ❌ 未解决 |

**说明**:
- 之前的 "107 ns 读取" 只测试了 100 keys 的纯 Cache 命中场景
- 真实场景 (100K keys) 下，FileKV 比 RocksDB 慢 240 倍
- **根本原因**: 多 segment 遍历、Bloom Filter 加载、锁竞争、内存分配开销

### 2. Bloom Filter 负向查找

| 场景 | FileKV | RocksDB | 差距 | 状态 |
|------|--------|---------|------|------|
| **Negative Lookup** | ~177 µs | ~247 µs | **1.4x 快** | ✅ 已验证 |

**说明**:
- FileKV 的自适应 Bloom Filter 缓存确实有效
- 但整体收益被其他开销抵消

### 3. 写入性能

| 场景 | FileKV | RocksDB | 差距 | 状态 |
|------|--------|---------|------|------|
| **Single Write (No WAL)/64B** | ~205 ns | - | - | ✅ 基准数据 |

## 🔴 已识别但未解决的性能瓶颈

### P0: SparseIndex O(n) 线性扫描

- **状态**: ✅ **已修复** (2026-04-10)
- **问题**: `SparseIndex.find()` 使用线性扫描，100K entries 需要 100,000 次比较
- **修复**: 改用 HashMap + 有序 Vec 混合设计，`find()` 改为 O(1)
- **验证**: 诊断测试显示 O(1) 特征（100 keys: 10.77 µs, 1000 keys: 9.87 µs, 10000 keys: 14.33 µs）
- **但**: 整体读取性能仍不足，说明还有其他瓶颈

### P1: 多 Segment 遍历开销

- **状态**: ❌ **未实现**
- **问题**: `get()` 需要遍历所有 segments，每个 segment 都要：
  1. 加载 Bloom Filter (如果未缓存)
  2. 查询 SparseIndex
  3. 读取磁盘 block
  4. 反序列化
- **影响**: 即使 Cache 命中，多次锁获取和函数调用累积开销巨大
- **诊断数据**: 即使预热 Cache，平均每个 key 仍需 9.21 µs（目标应 < 1 µs）

### P2: Block Cache 容量限制

- **状态**: ❌ **未实现**
- **问题**: 默认 `max_items = 10,000`，但测试有 100K keys
- **影响**: Cache 频繁淘汰，无法保持热数据
- **实验**: 增加到 150K 后，性能反而下降 (341ms vs 151ms)，说明 LRU 管理本身有开销

### P3: 锁竞争

- **状态**: ❌ **未深入优化**
- **问题**: `segments.read()` + `index_manager.read()` + `block_cache.get()` 多次锁获取
- **影响**: 并发场景下性能下降
- **已做**: 减少 `get()` 中的锁粒度，在循环外获取 locks

### P4: 内存分配开销

- **状态**: ❌ **未优化**
- **问题**: String 克隆、Bytes 克隆、Option 包装等
- **影响**: 高频调用场景下累积显著

- **文档**: `implementation_summary.md`

## ❌ 未实现的高优先级优化

### 1. Bloom Filter 预加载到内存

- **问题**: 当前 Bloom Filter 在首次访问时才加载
- **建议**: 启动时或 segment 打开时预加载所有 Bloom Filters
- **预期收益**: 减少 17-35 µs/key 的 Bloom Filter 加载开销

### 2. Segment 合并减少数量

- **问题**: 多个小 segment 导致多次查找
- **建议**: 更积极的 compaction 策略
- **预期收益**: 减少 segment 遍历次数

### 3. 零拷贝设计

- **问题**: 当前每次读取都要 Bytes::clone()
- **建议**: 使用 `&[u8]` 引用而不是克隆
- **预期收益**: 减少内存分配开销

### 4. 批量预取优化

- **问题**: 当前是单次随机读取
- **建议**: 检测顺序访问模式，批量预取
- **预期收益**: 利用 CPU 缓存行和磁盘预读

## 📝 总结

**FileKV 当前状态**:
- ✅ 架构设计合理 (LSM-Tree + Bloom Filter + Zone Map)
- ✅ INNO-001/002 创新优化已验证有效
- ✅ SparseIndex O(1) 优化已生效
- ❌ **真实场景下比 RocksDB 慢 240 倍**
- ❌ 多段优化已实施但未触及核心瓶颈

**诚实评估**:
- FileKV 目前是**学术研究原型**，不适合生产环境
- 核心读取性能需要 **15x 提升** 才能达到 RocksDB 水平
- 需要继续实施 P1/P2 优化，特别是 Bloom Filter 预加载和零拷贝设计
