# Redis 缓存策略

## 缓存模式

### 1. Cache-Aside（旁路缓存）

最常用的缓存模式：

```
读：先读缓存，命中返回；未命中读数据库并写入缓存
写：先更新数据库，再删除缓存
```

```java
// 伪代码示例
public User getUser(String id) {
    User user = redis.get(id);
    if (user == null) {
        user = db.query(id);
        redis.set(id, user, 3600);
    }
    return user;
}
```

### 2. Read-Through（读穿透）

缓存作为数据库的代理：

```
应用只与缓存交互，缓存负责与数据库同步
```

### 3. Write-Through（写穿透）

写操作同时写入缓存和数据库：

```
写：应用写入缓存，缓存同步写入数据库
```

## 缓存淘汰策略

| 策略 | 说明 |
|------|------|
| noeviction | 不淘汰，写满报错 |
| allkeys-lru | 所有键 LRU 淘汰 |
| volatile-lru | 有过期时间的键 LRU 淘汰 |
| allkeys-random | 随机淘汰 |
| volatile-ttl | 按剩余 TTL 淘汰 |

## 缓存穿透/击穿/雪崩

### 穿透：查询不存在的数据

**解决方案：**
- 布隆过滤器
- 缓存空值（设置较短过期时间）

### 击穿：热点 key 过期

**解决方案：**
- 互斥锁（分布式锁）
- 逻辑过期（不设置物理过期时间）

### 雪崩：大量 key 同时过期

**解决方案：**
- 随机化过期时间
- 多级缓存架构

## 与数据库一致性

| 方案 | 优点 | 缺点 |
|------|------|------|
| 先删缓存再更新 DB | 简单 | 可能脏读 |
| 先更新 DB 再删缓存 | 推荐 | 极端情况不一致 |
| 延迟双删 | 更一致 | 复杂度高 |
| Canal 监听 binlog | 最终一致 | 架构复杂 |
